# 13. Risks

| Risk | Concrete failure mode in Ledgerkit's case | Mitigation |
|---|---|---|
| Over-copying hledger architecture instead of designing Python-native equivalents | Translating Haskell's lazy, functional query-evaluation style directly into Python instead of an idiomatic AST/visitor; porting `regex-tdfa`-shaped code where Python `re` already does the job differently but adequately | `hledger-researcher`'s brief documents *intended semantics*, not implementation structure; the lead designs the Python implementation independently (`07-query-regex.md` §7.2's explicit separation of "understand" from "design"); `compat-differential-tester` verifies *behaviour*, never structure, so a differently-structured-but-behaviourally-identical implementation is never penalised |
| Accidental compatibility regressions | A Stage C/D refactor (e.g. `Query` → query AST) silently changes an already-`COMPATIBLE` behaviour | Every existing `COMPATIBLE`-classified feature gets a differential test *before* the refactor lands, run again after — `release-phase-auditor` blocks the phase if any previously-`final` register entry's tests fail |
| GPL/provenance mistakes | An agent translates hledger source without recording it as `directly_translated`, or copies an hledger manual example whose doc-licence was never checked | `10-source-assisted-development.md`'s five-category discipline + the open item to confirm hledger's doc/example licensing before first use (not yet resolved — a standing Stage A action item, not closed by this planning session) |
| Core becoming too heavyweight | A future Stage E/F/G phase adds a "just this one" dependency (e.g. a Decimal-adjacent math library) that quietly becomes load-bearing | `06-core-architecture.md` §6.2's CI import-graph check + `CLAUDE.md`'s existing Unauthorised Change Rule on `pyproject.toml`, extended with the licence-compatibility criterion (`02-licence-migration.md` §2.4) |
| Compatibility modes becoming excessively complex | Building the `hledger-2` profile scaffolding now, speculatively, before any concrete 2.0-targeting need exists | Explicitly deferred (`01-product-goal.md` §1.3, `06-core-architecture.md` §1.3) — architectural separation is planned, not built, until hledger 2.0 stabilises and a real need is demonstrated |
| Overfitting CodeCompass to Ledgerkit | CodeCompass grows an "hledger executable" or "accounting manual" concept that only ever fires for Ledgerkit | Not Ledgerkit's risk to manage directly — CodeCompass's own `reference-project-protocol.md` already names Technical Clipper as the generalisation cross-check; Ledgerkit's `context-curator` findings explicitly frame proposals as general capabilities (`05-context-curator.md` §5.5), never as "add hledger support" |
| Agent-generated graph noise | A `hledger-researcher` or `context-curator` suggestion gets treated as settled fact by a later session | `04-codecompass-integration.md` §4.4's deterministic/agent-suggested/verified/rejected states, never auto-promoted; same discipline applies to compat-register `status: proposed` vs `final` |
| Stale CodeCompass context | CodeCompass's graph reflects an older Ledgerkit dependency state (e.g. after a Stage E dependency change) | `context-curator` checks freshness as one of its explicit evaluation criteria (`05-context-curator.md` §5.2, `context_advantage_rationale`/`freshness` fields) every time it's actually used — no standing freshness-monitoring agent is created at current scale (§3.1's explicit deviation from CodeCompass's `context-health-planner`) |
| Documentation accretion | `dev-docs/hledger-compatibility.md` or `dev-docs/architecture.md` grows "note: since Stage N this also..." caveats the way CodeCompass's own `architecture/overview.md` did | `11-documentation-lifecycle.md`'s blank-slate reconstruction at Core 1.0 and Stage boundaries, plus the standing rule "if a paragraph is wrong, fix it, don't annotate it" |
| Indefinite expansion before Core 1.0 | Stage E/F/G scope creeps ("while we're here, let's also implement...") without ever reaching a Core 1.0 tag | `12-roadmap-migration.md` §12.5's explicit, checkable Core 1.0 criteria (not "every hledger feature") + the existing `CLAUDE.md` rule that milestones close only on explicit user confirmation, never inferred |
| **Licence-transition-specific: the GPL/library tension breaks `ledgerkit-editor` or third-party adoption without anyone deciding that on purpose** | Gate G1 resolves by default/inaction to "GPL, as literally specified," and `ledgerkit-editor`'s in-process-import architecture becomes legally incompatible with its MIT licence without an explicit decision to accept that trade-off | `02-licence-migration.md` §2.2's four explicit options, none of which are silently assumed — Gate G1 requires an affirmative choice, not a default |
| **Roadmap-migration-specific: Milestone 5 quietly disappears instead of being visibly superseded** | A future contributor searches `ROADMAP.md` history for "CLI filter flags" and finds nothing, assuming it was simply dropped | `12-roadmap-migration.md` §12.3 records it as "superseded by Stage C" explicitly, and the actual `ROADMAP.md` rewrite (Gate G4) must carry that supersession note forward, not delete the row |
